# Data

One file per experiment. `manifest.csv` is generated by
`scripts/build_manifest.py` and lists every file with the experiment it came
from, the GPU profile in effect, the producing script, its record count, and its
SHA-256.

Files are JSON Lines: one JSON object per request. Some files begin with plain
text state lines (the GPU profile in effect, a perplexity reference); readers
should skip lines that do not start with `{`, which is what the scripts here do.

## Fields

| field | meaning |
|---|---|
| `tag` | run label, usually `<profile>-<pass>/<position>` |
| `decode_tps`, `prefill_tps` | tokens per second, generation and prompt processing |
| `prompt_n`, `predicted_n` | tokens in, tokens generated |
| `decode_s`, `prefill_s`, `wall_s` | seconds |
| `draft_n`, `draft_n_accepted`, `accept_pct` | speculative decoding acceptance |
| `vram_mib`, `gtt_mib`, and their `_delta_` forms | memory, and the change caused by the request |
| `sha1` | SHA-1 of the response text, first 12 hex characters |
| `sha1_reasoning` | the same over the reasoning trace |
| `reasoning_chars` | length of the reasoning trace |
| `junction_c`, `overtemp_c` | junction temperature, and the guard trip value if any |
| `idle_w_ref` | idle board power measured before the run, for subtraction |
| `decode` / `prefill` | telemetry sampled during that phase, see below |

The telemetry block holds `n` (samples), `w_avg` / `w_max` (board watts),
`junction_avg` / `junction_max`, `edge_max`, `mem_max`, `fan_max` (rpm),
`busy_avg` (percent), `mv_avg`, `sclk_avg` (MHz), and `cpu_pkg_w`.

Idle files (`idle-power.jsonl`, `aspm-idle.jsonl`, `display-refresh-idle.jsonl`,
`idle-with-projector.jsonl`) use a different shape: `gpu_w_trapz` is the
trapezoidal integral of board power over `span_s` seconds from `n` samples, with
`gpu_w_med/min/max/sd` and median `mv`, `sclk`, `mclk`, `jt` alongside.

## Soak files

`soak-efficient-*-runs.jsonl` ends with a summary object whose `runs` array holds
one entry per request: `i`, `sha1`, `sha1_reasoning`, `t_rel`, `decode_tps`,
`predicted_n`, and a `decode` telemetry block. `reference-sequence-*.json` is the
plain list of `sha1` values the gate compares a later session against, position
by position. See [../docs/output-stability.md](../docs/output-stability.md).

`soak-efficient-ngram.log` and `soak-efficient-nospec.log` are the console output
of the same runs, kept unmodified. They carry a warning in Polish that the output
"is not reproducible under load", reporting 46 distinct hashes across 70 requests.
**That warning is a false alarm and should not be read as a result.** It was
printed by the earlier version of the gate, which compared every request in a
session against the first request in that same session. `llama-server` carries
cache state between requests, so those outputs are expected to differ; the
comparison measured the cache, not the hardware. The gate committed here
(`../scripts/soak-and-output-gate.sh`) compares matching positions across two
sessions instead and would not print that line. The logs are kept because they
are what the run actually produced, not because the warning stands.

## Provenance

`perplexity-chunks.txt` holds per-chunk perplexity values computed over the
wikitext-2 test split. The corpus text itself is not redistributed here.

The quality corpora and questions are synthetic, generated by
`scripts/gen_quality_corpus.py`. `quality-keys*.json` are the answer keys.

Names and locations appearing inside generated text in these files are
placeholders substituted for the originals before publication.

## KV cache-type files

`kv-nexttoken-*.json`, `kv-repeat-*-64k.json`, `kv-needles-turbo4.json` and
`kv-vision-*.json` come from the 128K cache-type round described in
[../docs/context-and-quality.md](../docs/context-and-quality.md). They are
single JSON objects rather than JSON Lines, written as the run produced them.

`kv-nexttoken-*.json` holds `test0` (three repeats of an 8K prompt on a warm
prompt cache), `test1` (one full recompute per context length) and `test2`
(recompute against half-cached reuse at 64K). Each record carries `top`, the
reported top-20 as `[token, logprob]` pairs, plus `logprob` and `tok` for the
sampled token, `dt`, `usage`, and a truncated `sha1` over reasoning and content.
`kv-repeat-*-64k.json` holds four such records under `runs`.
`scripts/kv_distribution.py` reads these and prints every figure quoted in the
document.

The prompts were frozen to disk before the runs so both variants read
byte-identical input. Their SHA-256 values, as `~/gate/f3-ctx-<len>.txt` on the
measurement host:

| length | bytes | sha256 |
|---|---:|---|
| 8K | 24265 | `84b930575f5bcb5e75004dc6d96528d88aa15d0def171fe3e3687fae8c2462f5` |
| 32K | 97330 | `5a0a6781024f9535648f2cad42860e16518213491f7604c95dcd5ebc97a026dd` |
| 64K | 194770 | `fea8e08de8fcaddc52c94523e356b3a4093f09e287999fe9b7047d3027bd506e` |
| 120K | 364678 | `568633ae46b955341cbbfb0cc692b28358df17d30a611b1fd1a6c9101db555a6` |

The filler text is generated by `build_n` in `scripts/kv_client.py`, so the
files are reproducible from the script and are not committed.

`kv-vision-img/t1.png`, `t2.png` and `t3.png` are the three generated images the
vision cases used; each record's `md5img` is the first eight hex digits of the
corresponding file's MD5. They are inputs, not measurements, so they carry no
manifest row.

### GTT at 128K

Both variants report about 997 MiB in GTT at `--ctx-size 131072`, which looks
like a spill to system RAM and is not one. It decomposes exactly into the host
buffers `llama-server` always allocates:

| buffer | MiB |
|---|---:|
| `CPU_Mapped model buffer` | 682.03 |
| `Vulkan_Host compute buffer` | 296.04 |
| `CPU compute buffer` | 24.93 |

The same `682.03 MiB` figure appears in a `--ctx-size 65536` log from the
earlier round, so it is not an artifact of the longer context. The startup log
places 66 of 66 layers on the GPU and every KV buffer on `Vulkan0`, and the runs
had `RADV_PERFTEST=nogttspill` set, under which an over-allocation fails instead
of falling back to host memory. Prefill throughput does drop with context
(694 tok/s at 8K to 311 tok/s at 120K), equally in both variants, which is
attention cost rather than a memory-path change.
